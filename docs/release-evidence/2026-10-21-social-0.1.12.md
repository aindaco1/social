## Certificate rejection

The application lockfile pins rustls-webpki 0.103.16 and webpki roots/root-certs
1.0.10. The opt-in `npm run desktop:test:tls` check exercises the application's
locked reqwest transport against all twelve published eMudhra TLS test paths.
Every path returned `CertDistrusted`; the valid HTTPS control succeeded. The
check rejects DNS, timeout and unrelated transport errors as incomplete evidence.

This is transport-level evidence, not a live provider operation through the UI.
No social post, provider message or diagnostics report was sent. The ordinary
Rust suite intentionally skips this network-dependent test; its separate passing
run is required evidence for this security release.

## Recovery and acceptance boundaries

All five public 0.1.11 assets were independently downloaded and matched their
GitHub SHA-256 digests. Its app passed signature, notarization and Gatekeeper
checks; DMG, ZIP and updater app contents matched. These retained assets are
recovery evidence, not a secure TLS fallback: 0.1.11 predates this certificate fix.
Prefer a forward repair; any downgrade needs a separate exposure decision.

Existing app data, Keychain credentials and the updater signing key are retained.
The prior-version updater smoke belongs on an isolated runner: the smoke path
initializes the normal app database, so staging its app bundle alone does not
isolate a real user's data. Public-asset inspection on the maintainer's Mac does
not launch the old app.

Real provider delivery, representative user-data/Keychain survival, VoiceOver,
independent clean/older-Mac acceptance and full-app/WebKit offline acceptance
remain separate open product gates. Native-helper offline checks do not establish
whole-app network isolation. No Intel/universal distribution is claimed.
